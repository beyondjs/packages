# Local workspace installation: validation

`beyond install` resolves a whole workspace — npm `workspaces` members, members outside the root declared through the labeled Beyond extension `beyond.workspaces`, several local versions of one name — into a portable lock (`beyond-lock.json`, `beyond-lock/2`), fetches its external closure into the user's source store, and writes the machine-local execution projection (`.beyond/execution.json`, `beyond-execution/1`) that the development service consumes instead of an application `node_modules`. [The local installation guide](../../docs/local-installation.md) specifies those contracts; this group validates them at the level of Packages' public modules, area by area, and accepts the owner's criteria for them in [`acceptance.test.mjs`](acceptance.test.mjs) and [`recovery.test.mjs`](recovery.test.mjs).

Every file runs under Node's test runner in its own process, against the implementation the bootstrap Engine serves from this checkout. Registries are in-process fixture registries on allocated ports; nothing reaches a public registry. What an installed toolchain does (`beyond install` and `beyond run` of the command line) is accepted by the command line's acceptance, never by this group.

## Prerequisites and commands

Every file runs from the Packages directory under BEE Node, as [the stage-1 validation](../stage-1/README.md) describes: `BEE_URL` names the bootstrap Engine serving this checkout and the utilities, and `BEE_NODE_DIR` a BEE Node checkout whose loader runs the file. Only `service.test.mjs` also needs `WATCHERS_URL`, the server of the watchers utility, because the host it starts runs the watchers service through it; no other file starts a watcher. Node 22.21.1 or later.

```sh
cd "$PACKAGES_DIR"
BEE_URL=http://localhost:1112,… node --import "$BEE_NODE_DIR/register.mjs" tests/local-install/<file>.test.mjs
BEE_URL=http://localhost:1112,… WATCHERS_URL=http://localhost:1120 \
  node --import "$BEE_NODE_DIR/register.mjs" tests/local-install/service.test.mjs
```

Each file is one process. Node's test runner takes several at once, still one process each, with `--test` before the files. The workspace declaration (`service/workspace/declaration.mjs`) and the context (`service/context.mjs`) are plain ESM of the development service: the files that exercise them import them by relative path, and their unit tests run with `node --test "service/test/*.test.mjs"`.

## Acceptance of the owner's criteria

[`acceptance.test.mjs`](acceptance.test.mjs) (discovery, installation, consumption) and [`recovery.test.mjs`](recovery.test.mjs) (freshness, failures) install [the acceptance workspace](fixtures/acceptance/README.md): two applications (React 19 and React 18), `@lt/message` 1.0.0 inside the root and 2.0.0 in a repository beside it, a consumer of each version, a view with React as a peer, an npm alias, a root development dependency, and a registry that also publishes newer releases of every local name as decoys.

| Group | Established |
| --- | --- |
| Discovery (criterion 1) | The npm workspace's members in declaration order with their ids, the member outside the root by `beyond.workspaces` with its canonical path, a negated pattern and a directory without a manifest excluded; the inputs the lock records, recomputed from their definition; npm's object form, a Beyond pattern outside the root, `beyond.json` and a standalone package; `WORKSPACE_CONFIG_CONFLICT`, `WORKSPACE_NAME_DUPLICATED`, `MEMBER_VERSION_MISMATCH`, `MEMBER_NOT_FOUND` and `WORKSPACE_INSTANCE_DUPLICATED` (naming both directories); a command finds the workspace from inside a member, reaches the member outside the root only with `--workspace`, and refuses an excluded package below the root (`CONTEXT_NOT_MEMBER`) |
| Installation (criteria 2, 4 and 5) | The whole workspace resolved and only its external closure fetched; no package document, manifest or archive of a local name requested, though the registry has newer satisfying releases; every metadata answer complete before the first archive is requested, and exactly the lock's archives requested; the lock's members, workspace nodes, external origins, integrity and archives, each consumer's edge to its own version, the alias with its declared name, the importer's own peer and one peer context per application, the root's build edge; a lock without paths of the machine, in canonical text, whose digest is that of its content; a ready projection that locates every node (members in place, externals in the store), answers every edge of the lock, resolves a node to itself and never guesses (`DEPENDENCY_NOT_INSTALLED`, `PEER_CONTEXT_AMBIGUOUS`); one counter view bound to React 19 in one application and React 18 in the other, with one React per renderer pair; a frozen reinstall with no request and a byte-identical lock; the same workspace resolved from scratch elsewhere giving the same lock byte for byte from stored sources; a second project sharing the store with another React patch, its own projection and the shared scheduler stored once; an offline installation of a frozen workspace with no request; nothing written into the member outside the root by any of them, and no `node_modules` |
| Freshness (criteria 5 and 9) | A changed member dependency makes the projection stale (`member:<id>`), and the reinstall follows the new edge while keeping the locked React though a newer one is published, until `update`; a changed or absent lock makes it stale (`lock`), an absent one is `missing` and an unreadable one `incompatible`; removing a stored source, or only its files, makes it `incomplete` (`SOURCE_MISSING` naming the node), and the reinstall fetches only that source; offline, inputs the lock does not cover and a source missing from the store are `OFFLINE_UNAVAILABLE` with nothing written or requested, and the next online installation recovers |
| Failures (criterion 9) | A package no registry has, a corrupt archive, an interrupted transfer, an unreachable registry, a local range no member satisfies (`WORKSPACE_RANGE_UNSATISFIED`, though the registry has one) and a `workspace:` specification no member provides (`WORKSPACE_PACKAGE_NOT_FOUND`) each report an invalid installation that wrote nothing: no lock or projection where there was none, the previous ones byte for byte where there were, no source of a refused archive in the store; after a refused archive the next installation fetches only what was missing; concurrent installations through one instance are serialized (one resolves and writes, the other is frozen); a stage a killed download left behind is removed by the next fetch, one still in use is kept, and no stage is ever published |
| Consumption (criteria 3 and 4) | The Packages workspace built from the members and the projection resolves `@lt/message/text` to version 1 for one application and to version 2 for the other application and for `@lt/banner`, answers an external import with its node, and refuses an undeclared one; without the projection, the name two members hold resolves to neither (`PACKAGE_AMBIGUOUS`) |

## CDN parity (criterion 10)

[`../cdn-resolution/workspace.test.mjs`](../cdn-resolution/workspace.test.mjs) installs the same workspace, then pins each application's external roots with `Resolution.pin` as CDN does: every pinned release is in the lock with the same key, origin, visibility, integrity and archive, every root is the node the application's edge reaches, and every pinned edge is in the lock, a peer's context aside (the application in the lock, the root selection in a pinned graph, by design). A private release from a registry that requires a credential is stored for the local tenant only and no credential is written into the lock or the projection, and a CDN tenant fetching the same release into the same store downloads a copy of its own. `Resolution.pin` refuses `workspace:` as a root and as a dependency a registry package declares, requesting nothing for the name it names, and `Sources.fetch` refuses a graph holding workspace nodes and stores nothing for them.

## What a pass establishes, and what it does not

A pass establishes the behavior of Packages' contracts on one machine against fixture registries: discovery, the graph, the lock, the store, the projection and their consumption by the Packages workspace, the routes and the service. It does not establish an installed toolchain's `beyond install` or `beyond run` (the command line's `install` acceptance group), a browser loading the installed graph with updates (criteria 6 to 8, the `local-install` case of the command line's `web` group), a public registry, git or archive URL sources in a workspace, installations of one workspace from several processes at once, or anything hosted. Each file's header and its fixtures README say what it covers beyond this summary.
