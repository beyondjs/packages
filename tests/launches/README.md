# Launch validation

Validates the launch of execution targets (`beyond-launches/1`, [the guide](../../docs/launches.md)) at two levels: the feature of the host with stand-ins for what surrounds it, and the real development service of this checkout with the real catalog of applications, the BEE Node registration, the command line's launcher and, when one is given, a real Deno 2.

## Run

From the Packages directory:

```sh
node --test "service/test/launches*.test.mjs"
node --test tests/launches/service.test.mjs
node --test tests/launches/versions.test.mjs
BEYOND_DENO=<Deno 2 executable> node --test tests/launches/deno.test.mjs
```

Expected: every test passes; `deno.test.mjs` reports its one test as skipped, with the reason, when `BEYOND_DENO` does not name a Deno 2 executable.

Prerequisites of the real-service files: Node 22.21.1 or later and the checkout's dependencies, its bootstrap included, as for [tests/portable](../portable/README.md); the BEE Node checkout (`BEE_NODE_DIR`, or `bee-node` of the suite beside this repository), the command line's checkout (`BEYOND_CLI_DIR`, or `cli` of the suite) for `src/launcher.mjs`, and the development runtime (`BEYOND_RUNTIME`, or `local-2026` of the suite), which the fixture is assembled against. Each file starts its own services, whose first start compiles Packages with Engine; `BEE_HTTP_TIMEOUT` is raised to 180 s for the loader of the host unless it is set.

## What each file establishes

| File | Established |
| --- | --- |
| `service/test/launches.test.mjs` | A backend target runs under the registration with the loader of the service (`BEE_URL` its origin, `BEE_ADAPTER=packages`, `BEE_IMPORT_MAP` empty), in the root, without the service's settings and credentials, with the target's variables of the settings feature, which never replace the loader, the reserved ones (`BEE_URL`, `NODE_OPTIONS`, `DENO_DIR`) left out and said in the launch's `diagnostics`; it is `ready` only once its readiness appears and serves what the case asks it; `launch.changed` follows `starting`, `running`, `ready`, `stopping`, `exited`; a stop ends it with `SIGTERM`, a second stop is `LAUNCH_ENDED`; the same request identifier is the same launch, another request while it runs is `LAUNCH_RUNNING` with it, the identifier of another target is `IDEMPOTENCY_KEY_REUSED`, and two simultaneous requests start one process; a process that ignores `SIGTERM` ends with `SIGKILL` once `BEYOND_LAUNCH_STOP` passed; a process that ends by itself fails with the end of its output, one that finishes its work exits, a readiness without a final newline is observed; a missing Deno executable is refused at the launch (`DENO_INVALID`) and nothing starts; the end of the service ends every launch, the one that ignores `SIGTERM` included, within its bound; a launch ends although a process it left behind keeps its output open |
| `service/test/launches.routes.test.mjs` | A service without the `launch` setting mounts no route, claims no capability and starts nothing (PKG-A10); a setting without absolute paths and a service that neither pairs nor verifies delegated grants, a loopback one included, fail the start; behind a public origin, on another address or behind grants that let no loopback request through, a launch is refused before any process starts (`LAUNCH_CONSUMER_REFUSED`), and grants that trust loopback requests launch; the refusals of a request (identifier, body, size, content type); frontend, unresolved, unsupported-runtime, Deno-not-configured, unknown and catalog-less targets refused with their reasons, the identifier of a refused request decided again; unknown and malformed launch identifiers and output cursors; a caller the policy did not admit refused; a host that gives no origin launches with the origin the request reached |
| `service/test/launches.deno.test.mjs` | A Deno target runs the configured executable (a stand-in that reports what it was given) with `run --no-config --no-lock --allow-net --allow-import --allow-env --reload=<origin>/ --import-map=<origin>/importmap.json?target=node&format=esm`, the feature's entry module and the specifier, `DENO_DIR` in `.beyond/launches/deno`, and stops; the executable of the setting comes before the environment's; without one the target is refused and nothing is created; the executable is checked at every launch, so one replaced by a Deno 1 since the last launch is refused (`DENO_INVALID`) |
| `service/test/launches.bounds.test.mjs` | A catalog that never answers is answered `UNAVAILABLE` within the bound and frees the target; an executable that cannot be started fails the launch without a process; a request that waits for another of its target is decided after it (`LAUNCH_RUNNING`, the catalog not asked); the ended launches kept are the latest ones, and the identifier of a forgotten one launches again; a request whose target the catalog resolves after the end began, one queued behind it and one sent after it are `UNAVAILABLE` and start no process; the end stops what lives and leaves no process the registry may signal |
| `service/test/launches.output.test.mjs` | The ring of the last lines, their numbers and what a reader lost; lines as a terminal shows them (control sequences, carriage returns, the width); an incomplete line observed and made a line at the end of its stream; announcements at most once per cadence |
| `service/test/launches.command.test.mjs` | How a resolved target becomes a launchable one and why one is not, and that of two local versions it launches the versioned specifier the catalog resolved (`launch.specifier`); the catalog's refusals and outage; the Node command and its environment, the reserved variables of the settings left out and said; the Deno command, the order its executable is read in, its check at every launch (`DENO_INVALID`, nothing created) and the `.gitignore` of the state directory; nothing launched before the service listens |
| `tests/launches/service.test.mjs` | The real service: started without the setting it has no `/launches` and no `launch` capability (PKG-A10); started with it, the backend target of the fixture starts with the real catalog, registration and launcher, is ready on its declared text, answers its HTTP route from the launched process with the `packages` loader, is not started twice for one request, refuses a second launch, is announced on the event stream of the development extension and stops with code 0, its process gone; a frontend target is refused (`TARGET_FRONTEND`), a Deno one without an executable (`DENO_NOT_CONFIGURED`), an undeclared one is `TARGET_NOT_FOUND`; a page of another site reaches no launch route |
| `tests/launches/versions.test.mjs` | The real service over a copy of the fixture with a second local version of `@launches/api` (2.0.0, whose server says a readiness of its own) and a target that selects it: the catalog resolves `launch.specifier` to the versioned specifier, the launch imports it, and the version it selects is the one that says it is ready, answers and stops with code 0; the target that selects no version is `TARGET_AMBIGUOUS` and not launched |
| `tests/launches/deno.test.mjs` | With a real Deno 2: the Deno target of the fixture loads the compiled modules through the service's Node import map, is ready, answers from Deno, keeps its module cache in the workspace and stops with code 0 |

## Fixtures

[fixtures/](fixtures/README.md): the workspace the real service serves and the stand-ins of the unit tests. The harnesses copy what they run: [support/served.mjs](support/served.mjs) copies the workspace and the development runtime into a unique temporary directory with its own `BEYOND_HOME`, starts the service as `beyond run` does and stops it by detaching its owner; [support/stage.mjs](support/stage.mjs) mounts the feature on an Express application of its own with stand-ins for the catalog, the settings feature, the events and the origin, removes its temporary root after each case, and copies the stand-in Deno executable to a directory of its own when a case needs it.

## Not covered

Nothing hosted, no Windows process groups, and no process the host leaves behind when it is killed with `SIGKILL`. The command line's `targets` acceptance group runs the same journey from an installed `beyond run`.
