# packages agent instructions

For CDN v1 work, read the [maintained implementation contract](docs/cdn-contract.md); preserve its stage boundaries and distinguish approved scope from source evidence and unvalidated capabilities.

Canonical instructions for this repository and its descendants. Tool-specific files must only reference AGENTS.md. This is an independent Git repository; the current coordinated branch is `feature/next`.

Packages is a Beyond-authored packaging implementation and owns Dev Server/File API. Read [the service ownership contract](docs/development-server.md), including [local storage](docs/development-server.md#local-storage): reuse compiler/graphs and legacy capabilities, validate delegated access without per-container roles authority. Workspace owns frontend and central administration; Docker is required for Workspace projects locally/cloud, not standalone CLI. Read [development](docs/development.md), [architecture and SDK](docs/architecture.md) and [programming conventions](docs/programming.md) before changing its contracts. Engine compiles/serves the implementation as ESM for modern BEE Node execution; Packages itself must compile/serve the target widget app and shared module. Legacy-BEE fixtures do not select a different runtime. Preserve public/internal module boundaries and the runtime, types, styles and HMR acceptance criteria described locally.

Two authoring models coexist and must not be mixed. This implementation is authored for the existing engine that compiles it, with its export markers and manifests. The packages Packages compiles declare their public modules through package `exports` entries whose targets are entry points, module manifests that add their specification, and a package default bundler; they do not use export markers. [The first-stage validation](tests/stage-1/README.md) executes that contract end to end, from discovery to the update of a running consumer, and is the reference to run and extend when changing discovery, bundlers, processors, assembly, artifacts or watching.

- Use English for first-party docs, instructions, comments, docstrings and new explanatory text. Preserve intentional locale catalogs, public names/specifiers/paths, protocol keys and functional test values unless a compatibility change is explicitly authorized. Do not rewrite vendor, generated, lockfile or third-party content for language cleanup.
- Preserve current uncommitted work and repository history. Do not commit, push, reset, publish or deploy without explicit task authorization.
- Keep public Beyond module imports distinct from internal relative source imports. Do not silently replace the configured bootstrap, runtime or framework.
- Implementations of bundlers, processors and services are loaded with native dynamic imports, so the loader of the running process decides where they come from. Do not reintroduce legacy global import helpers, hardcoded resolution or test-only mappings to work around a missing integration.
- The File API, change events, build correlation and delegated-grant verification are the public module `@beyond-js/packages/development` (`modules/development`), specified by the [development contract](docs/development-contract.md) with its schema, fixtures and scenarios under `contracts/development`. The hosting service mounts it through its extension hooks; keep it free of compilation, resolution and any user or role store. Change the contract, its fixtures and `tests/development` together, and run that validation under BEE Node with a bootstrap Engine serving the implementation. The same module owns the located build diagnostics (`file`, `range`, `revision`), the declaration route (`GET /declarations/<specifier>`, the public declaration of a workspace or supplied module, tagged with the hash the build names), the explicit development selection and the preview entry document, which routes selected modules to the environment and everything else to the configured CDN origin with addresses relative to the document; [the preview validation](tests/preview/README.md) executes them with the real service, a real browser and the development runtime, and validates the Workspace template with an installed toolchain. Run it after changing the selection, the preview, the builds, the update route or the runtime's connection, and never report a reload or a rebuilt artifact as an update.
- `modules/bundlers/esbuild` is a trial of the esbuild packaging mode, not an adopted path, selected per module like any bundler. Read [its architecture section](docs/architecture.md#esbuild-bundler-the-packaging-mode-trial) and [its validation](tests/esbuild-packaging/README.md) before changing it. Its compiler is selected explicitly and reported in every artifact: keep it without a default or fallback, keep the mode out of the public address of a module, and do not present a rebuild as HMR, because nothing delivers or applies updates for packaged modules yet. Beyond divides code by public module only: never enable code splitting, emit private chunks or compile several public modules together.
- The `ts` bundler compiles the stylesheets (`styles` processor: Sass, Tailwind from the sources a manifest declares), the Vue and Svelte components (`vue`, `svelte` processors) and the public declaration (`types` conditional, `tsc` processor) of a module, and the SDK assembles internal modules, stylesheets, declarations and the widget registration of a manifest ([architecture](docs/architecture.md#styles-framework-sources-and-declarations)). Every platform a browser can be given also builds a production conditional — `web/production`, and `default/production` for a module that declares no platforms, which is how a stylesheet published through `exports` is authored — the same composition minified, without a source map or an update patch; a request for production output is answered only from one of those, never from a development conditional. [The styles and SDK validation](tests/styles-sdk/README.md) executes that path with the real watchers service; run it after changing a processor, the assembly, the manifest discovery or the processor lifecycle. The packages the toolchain supplies to every workspace (the development runtime, Widgets and its adapters) are compiled the same way, unwatched; the installed packages a browser needs are compiled by [`Delivery.installed`](modules/artifacts/installed.ts), one public subpath at a time, with subpaths that share a runtime delivered as one carrier and its facades. Browser behavior is accepted by the command line's `web` acceptance against an installation, never by these validations.
- Composed modules select their runtime with the `runtime` setting of their bundler, and their updates are delivered by the provisional `/u/` route. [The unified-runtime validation](tests/unified-runtime/README.md) executes both with the development runtime (`local-2026`), through the real development service; run it after changing the ESM assembly, the artifacts' dependency classification, the HTTP routes or the development events. The route stays outside `/m/`: the compiled-module contract belongs to `artifact-api`.
- A package declares how its public modules are compiled, and preparing it for delivery honours that declaration: a `source` package whose module selects a bundler of its own is compiled by that bundler, through the same `Compilation` the development service uses, and not by the compiler the consumer selected. Read [publication forms, analysis and generated outputs](docs/cdn-outputs.md#compilation-by-the-bundler-the-package-declares) and run [the preparation validation](tests/preparation/README.md) after changing `modules/analysis`, `modules/generation`, `modules/publication` or the assembly of a composed module; raise `Toolchain.COMPOSITION` when a composed output stops being compatible with one generated before it. These are contracts of Packages: CDN and any other consumer call them, and nothing in them knows which one.
- The utilities this implementation runs on (`@beyond-js/dynamic-processor`, `@beyond-js/finder`, `@beyond-js/watchers`) are served from their sources by the bootstrap, selected with `BEYOND_LOCAL_PACKAGES` ([the bootstrap guide](bootstrap/README.md)). [The utilities validation](tests/utilities/README.md) reports which copy of each one a run executed and repeats the edit, failure, stylesheet and manifest-reload scenarios, because what it checks was intermittent. Never report a repair in a utility as delivered without the identities of the run that exercised it.
- Test files are not sources: a processor leaves `<name>.test.*`, `<name>.spec.*` and the contents of `__tests__` and `__fixtures__` directories out of its inputs unless the module manifest sets `"tests": "included"` ([Tests](modules/sdk/conditional/processor/sources/inputs/tests.ts)), and the artifact of a `ts` module names every source of its map by absolute path, with the creator boundaries mapped to the ends of each source ([Mapping](modules/sdk/conditional/esm/mapping.ts)); a written artifact names them relative to itself ([Files.portable](modules/artifacts/files.ts)). Read [source maps and test files](docs/architecture.md#source-maps-and-test-files) before changing the assembly, the input selection or the artifact writer; the command line's `testing` and `delivery` acceptance groups execute both against an installation.
- A compiler whose process ends is reported as `COMPILER_UNAVAILABLE` and released, so the build fails now and the next one has a compiler again; [the compiler validation](tests/compiler/README.md) executes it with a controlled termination and, inside a Linux cgroup v2 with `memory.max` set, with the kernel's memory controller ending the compiler (`tests/compiler/oom.mjs`, which reports `BLOCKED` anywhere else). Raise `Toolchain.SHARING` whenever the delivery plan of an npm package ([Sharing](modules/analysis/pinned/sharing.ts)) or the union it compiles changes, as `Toolchain.COMPOSITION` is raised for composed outputs.
- Read the relevant maintained references before architectural changes; label source findings, runtime evidence and proposals accurately. Use targeted validation for behavior changes; documentation/comment edits do not require unrelated builds or services.
- [`service/`](docs/service.md) is the development service, exported as `@beyond-js/packages/service`, and [`bootstrap/`](bootstrap/README.md) is the transitional `@beyond-js/packages-bootstrap` package. Both are plain ESM run by Node as installed, not Beyond modules compiled by Engine: do not move them under `modules/` or import them through the loader. Everything that knows about Engine stays in `bootstrap/`; the service only chooses, through `Implementation`, between a compiled distribution and the bootstrap, and its discovery, attachment, lifetime and cleanup must not depend on which one ran. Do not add Engine-related dependencies to the root manifest. Unit tests run with `node --test "service/test/*.test.mjs"` and `npm test` in `bootstrap/`; behavior is accepted through the command line's acceptance suite against an installation, and an Engine-independent compiled distribution is not yet produced or validated.
- Keep instructions concise here and link maintained documentation. Before editing nested areas, read any applicable nested AGENTS.md. Do not apply sibling repository instructions globally.
- Test the public contract of every Beyond package or module you implement or change, its error and recovery cases included, following the Beyond testing conventions: Node's own test runner, one process per file; the bare specifier a consumer imports, never a source file or a relative path into a module; promises, events and readiness awaited rather than time, with a bounded wait that fails instead of hanging; whatever a test creates removed with `t.after`, on failure as well; temporary, unique directories and allocated ports; every case asserting its outcome, an error path by its code. A package that the Packages development service compiles is tested with `beyond test`; one that another compiler serves runs its `node:test` files against the modules that compiler serves. Existing suites adopt the conventions when they are changed.
- Follow the [coding standards](docs/coding-standards.md); they are binding for new and modified code. Source files target 300 lines or fewer and must not exceed 400. Model each responsibility as a class that owns `#private` state and exposes simply named members, composed from collaborating objects. Avoid compound names in methods, properties, variables and parameters by giving the responsibility its own object: `client.register()`, not `registerClient()`. Compound names remain allowed in class definitions. Preserve public contracts, and do not rewrite untouched files only to comply.

Documentation follows [the local documentation standards](docs/AGENTS.md).
