# Development contract: files, events and builds

`beyond-dev-files/1` is the versioned contract of the Dev Server's source operations, change events and build correlation. Packages owns it, as described in [Dev Server and File API](development-server.md). This guide explains the rules; the machine-readable parts live in `contracts/development`:

| File | Content |
| --- | --- |
| `schema.json` | JSON Schema 2020-12 definitions: `path`, `revision`, `cursor`, `tree`, `mutation`, `result`, `batch`, `event`, `build`, `diagnostic`, `selection`, `preview`, `output`, `composition` |
| `fixtures/valid`, `fixtures/invalid` | Documents named `<definition>.<case>.json` that must pass or fail their definition |
| `scenarios.json` | Behavior every implementation must reproduce: conflicts, external writes, replay, gaps, stale builds, access, the development selection with its externals, the preview entry and the composition document |

**Status: implemented by the public module `@beyond-js/packages/development`** (`modules/development`), with the limits listed under [Implementation and limits](#implementation-and-limits). The hosting development service mounts it as an extension; nothing in it compiles, resolves or stores users and roles.

The same module serves the catalog of the applications and execution targets a workspace declares (`beyond-applications/1`, `GET /applications`), which reads and writes their declaration through this File API, with its revisions, and announces its changes on this event log as `applications.changed`: see [applications and execution targets](applications.md).

## Identities

A **path** is relative to the served root, uses `/`, and has no empty, `.` or `..` segment. It names a file. It never names a public module: module identity stays with `Identity`, `ModulePath` and `Selector`, and a file does not become a public module by existing.

A **revision** is `sha256-<hex>` over the file bytes. It is the same value, unquoted, as the HTTP entity tag of the file. Directories have no revision. A revision identifies content, so writing identical bytes yields the same revision and announces no change.

A **cursor** is `<epoch>:<seq>`. `seq` orders every event of one epoch. The epoch changes whenever the server cannot vouch for continuity: process start, watcher failure, or an event log that dropped entries a subscriber might still need.

## Reading

`tree` answers with entries and the cursor they are exact for; events after that cursor apply on top of it, which makes every tree a snapshot boundary. `scanned: true` means disk was re-read for this answer. Polling and manual refresh request a scan, so a change the watcher never delivered is still found; it is then announced with origin `scan`.

## Mutations and conflicts

Every mutation states what the writer believes is on disk: `expected` is a revision, or `absent` for a creation. There is no unconditional write. The server compares `expected` with the bytes on disk at the mutation boundary, not with a watcher-fed index, because agents, Git and other tools write without passing through this API and no API lock can serialize them.

| Outcome | Meaning |
| --- | --- |
| `completed` | The bytes are durably written; `revision` and `cursor` identify the result |
| `conflict` | Nothing changed. `conflict.expected` and `conflict.current` let the client compare; `current: "absent"` means the file is gone; `target` names an existing rename destination |
| `failed` | Nothing is promised; `error` explains |
| `skipped` | A batch stopped before this mutation |

Writes replace the file atomically (temporary file and rename in the same directory), so a reader or a crash never observes a missing or half-written file. A rename never overwrites its destination. Deleting or renaming requires a revision: a file that is already gone is a conflict, not a silent success.

A **batch** is ordered and not atomic. It stops at the first mutation that does not complete and reports `partial`: earlier mutations stay on disk, later ones are `skipped`. A `batch.completed` event marks the end of its changes so that a build does not snapshot the middle of a multi-file edit.

## Events

Events are delivered in cursor order. `file.*` events carry `origin`:

| Origin | Source | Knows the author |
| --- | --- | --- |
| `api` | A mutation of this API; `actor` is copied from the verified grant, including the task of an agent | Yes |
| `external` | The watcher observed a write that bypassed the API | No |
| `scan` | A comparison of disk with the index found it | No, and not the time either |

An `api` mutation that the watcher also observes is announced once. An external move is announced as `file.deleted` plus `file.created`, because a watcher cannot prove identity across paths; `file.renamed` exists only with origin `api`.

A subscriber presents the last cursor it processed. Within the same epoch and the retained log it receives exactly the later events; a client ignores any event whose `seq` is not greater than the last one it applied. Otherwise the first event is `resync` with reason `EPOCH`, `GAP`, `OVERFLOW` or `WATCHER`, and the client reads a scanned tree and reconciles against it. The server never claims that watcher delivery is lossless.

Some events of the hosting service are transient (`Log.notify`, `Development.TRANSIENT`): `launch.output` and `operation.progress`. They reach the open subscribers in order with the others, carry the cursor of the last stored event and take no number, and are never kept or replayed, so frequent ones never push the source events out of the retained log nor change what `changed()` tells the builds. A subscriber therefore passes them on whatever cursor it applied, and never adopts their cursor as its position: one that drops an event whose cursor it already covers never receives them. A client that reconnects recovers what they said from their routes (`GET /launches/:id/output?after=`, `GET /operations/:id`).

Editor buffers are client state. The contract gives a client what it needs to keep a dirty buffer safe: the base revision it loaded, a change event or conflict result carrying the current revision, and the content to compare. A client never discards a dirty buffer because an event arrived.

## Builds

A build records `input`, the cursor it read its sources at, and `files`, the files whose changes since the previous build it compiled (absent for a build nothing changed for), which is what a terminal or a client names when it says what an update applies. `build.started` and `build.ended` carry the whole build document. A build that ends after a newer change to one of its input files ends `superseded` and is never reported as current. A diagnostic that a processor reports on a source file carries `file` (relative to the root), `range` (one-based line and column), `revision` (the revision the index holds for that file when the build reports it, which is the compiled text unless the build is `superseded`) and `frame`, up to three lines of the file around the line (the line before, the line and the line after, read when the build reports it, absent for a file larger than 1 MiB or that cannot be read), so a client opens the file at the position, shows the code under the message and tells a diagnostic about old text from one about the text on screen. A diagnostic about a file outside the root, such as one of a package the toolchain supplies, or about no file at all, carries the message only; every message keeps the file and the position as text. Every diagnostic has its `severity` (`error` or `warning`).

Each problem is listed once ([Report](../modules/development/report.ts)): two reports with the same file, range and message are one, whichever platform or public module met it, and a syntax error that the transformation reports (`TRANSPILE_ERROR`) and the type check reports again under its own code (`TS1005`) keeps the transformation's code. The message starts with the versioned specifier of the first module that reported it, and `modules` names the others, so a consumer that filters the diagnostics of one module (the development runtime does) finds the problem under each of them. A diagnostic without a file is identified by its code and message. The type errors of a package the toolchain supplies (the development runtime, Widgets, the framework adapters; `supplied` in the facade's list) are the toolchain's defects and are not reported against the workspace's build; a module of such a package that does not build is, because a page that imports it cannot run. A module without TypeScript sources, such as a style module, declares nothing and reports nothing for it.

A module is built for every platform it declares, `node` and `web`, and `modules` lists it once for each with its `platform` and the hash of that artifact. A Node consumer and a browser preview each apply the artifact of their own platform, so one hash per module would announce to one of them an update that the update route then refuses. A platform that a module does not declare is not a failure: it is left out. A module that declares neither is listed once, `invalid`, without a platform. A source error that every platform meets is reported once.

A module is also checked: its `types` conditional builds a TypeScript program over its sources and the declarations of the workspace modules they import, and emits the public declaration of the module. A module that checks carries `declaration`, the hash of that declaration, on each of its platform entries. A type error does not invalidate the artifacts, because the compiler that produces them does not check types: the entries stay `valid` without `declaration`, the type errors are reported with their file and position, and the build is `failed`. A consumer applies artifacts by the status of their entries and shows the diagnostics; it does not treat a failed build as one without artifacts.

A module whose sources produce a stylesheet also carries `styles`, the hash of that stylesheet. It changes with the stylesheet alone: a consumer that holds the sheet, adopted in a widget root or linked by the document, replaces it when that hash changes even when the code of the module did not, and requests it from the update route by that hash (`/u/<styles hash>/…/styles/<subpath>`). A module compiled in the esbuild packaging mode, whose code receives no update in place, receives its stylesheet this way. A style module of that mode has a stylesheet and no code: it is listed `valid` with `styles` and without `hash`.

Saving a file, completing a build, delivering an artifact and applying an update in a runtime are four different facts. This contract reports the first two. Artifact delivery is the compiled-module contract; applying an update is reported by the runtime.

## Development selection

The **selection** says which packages and public modules of the workspace are in development. It is what the preview reads to decide where each module comes from: a selected module is served by this environment, and everything else comes from the CDN. Its **externals** say where the preview loads the installed packages that the workspace does not contain and this environment could compile itself (React, Vue, the libraries of the framework adapters): `environment`, the default, serves them here, as a preview always did; `cdn` addresses them on the CDN at their installed exact version ([Preview entry](#preview-entry)).

Only a request that replaces the selection changes it. Reading, opening, editing, creating or building a file never does. Until somebody selects, `explicit` is `false`, `externals` is `environment` and every package of the workspace is in development, because a package that was never published has no other place to come from. A replacement states the whole selection: it names packages, public modules or both, and `externals` when it is `cdn` (a replacement that names none is `environment`, and one that names another value is refused with `SELECTION_INVALID`); a name the workspace does not declare is refused with `SELECTION_INVALID` and its `unknown` list, and nothing changes. Selecting the externals keeps the packages in development only if the replacement names them, so a client that switches the externals sends the packages and modules it read back with them. A selected name whose package later disappears, for example with a branch change, selects nothing, is reported in `unknown` and is kept. Every change is announced as `selection.changed` with the new document. A document that is already open keeps the import map it was loaded with.

The selection is state of the working copy, not source. It is kept in `.beyond/development/selection.json` under the served root, which is the durable volume of a project environment, so it survives a new container, while the home of the service is disposable. The `.beyond` directory ignores itself for Git, is never listed, watched or announced, and a path into it is `PATH_FORBIDDEN` like the repository internals, so no file operation can change the selection.

## Preview entry

`GET /preview/` answers the entry document of the application of the workspace: an import map and one module script that imports the entry module. Importing it runs its top-level code once, which is what executing a public module means; no exported function is called. `GET /preview/entry.json` is the same information as a `preview` document, for a client that shows where each module comes from; its `selection` says whether somebody selected and the externals it was routed by. `GET /preview/composition.json` is the composition of the same entry ([below](#the-composition-document)).

| Module | Address |
| --- | --- |
| In development (selected) | `../m/<package>@<version>/modules/<subpath>?<development browser options>`, relative to the document, with its `vspecifier` |
| A package the toolchain supplies (the development runtime, the Widgets package, the framework adapters) | The environment: those packages are compiled and served like the packages of the workspace, so a project needs no copy of them |
| A package the workspace does not contain but that is installed for the package that imports it, or with the service (React, Vue, Svelte and the libraries the adapters depend on) | The environment, at the installed version: the service compiles the public subpath of the installed package for browsers on request, with its bare references kept and its CommonJS shape adapted, as the CDN generation does. Its stylesheet, when it has one, is served too |
| A workspace package that is not selected | The CDN origin, the same path, the version in its `package.json`, the published defaults of the options |
| A package neither installed nor contained | The CDN origin at its **resolved** version: a declared dependency that is an exact version |
| Anything without an exact version or without a CDN origin | No address: `source: "unresolved"` with the reason, a `PREVIEW_VERSION_UNRESOLVED` or `PREVIEW_CDN_UNSET` diagnostic, and no import map entry |
| Any package of the graph of an installed workspace (a member, or a node of the source store) | The environment, as the importer's edges select it; nothing of the graph is asked of the CDN |

Every address names the source of its package, as the paths of the compiled-module contract do: npm and the workspace unprefixed, another registry by its id. An installed package is addressed by the registry its lockfile recorded, which the host reports (`origin` of its facade), or in an installed workspace by the provider of its node; a workspace package that is not in development is addressed on the CDN under the registry its `publishConfig.registry` declares, or npm; a package installed from Git or from an archive address has no address, and is `unresolved` with a `PREVIEW_SOURCE_UNSUPPORTED` diagnostic. An installed package is resolved from the package that imports it, and what it imports from its own installation, so two importers can reach two versions of one specifier: the first is the import, and the importer that reaches the other one gets it in `importmap.scopes`, keyed by the package prefix of its address (`../m/<package>@<version>/`, or its address on the CDN), as a release scopes it. `modules` then lists both versions.

The stylesheets the sources of a module select by specifier (`import 'pkg/sub.css'`, which the build keeps out of the code and names apart) are listed under `stylesheets` of that module, each with the address of the stylesheet of `pkg/sub` (or of the literal subpath `./sub.css` when the package publishes one), and the specifier enters the import map with that address. The document links those of the modules in its scope, marked with the versioned identity of the module whose stylesheet it is, which is what the development runtime replaces; a widget adopts its own. The stylesheet of every module that has one is in the import map as `<specifier>.css` (a specifier without `.css` never resolves to a stylesheet), so the runtime finds a sheet with `import.meta.resolve`. When a widget of a package is reached and the package publishes the optional `./global` style module, which nothing imports, that module is described in `updates.session` and mapped as `<package>/global.css`, so the runtime addresses its updates from the session. A style module is never an entry candidate.

A module served by the environment whose sources produce a stylesheet carries `styles`, the address of that stylesheet relative to the document, `widget: true` when it declares a widget, and `scope`: `document` when the entry reaches the module without crossing a widget, `widget` otherwise. The document links the stylesheets in its scope in its head, each link marked `data-beyond-styles="<vspecifier>"`, which is what the development runtime replaces when a build changes the sheet; a widget adopts its own sheets and those of its dependencies inside its shadow root, so a stylesheet reached through a widget only (the sheet of a module that a widget imports) is not linked by the document.

The CDN origin is configured with `BEYOND_CDN_ORIGIN` in the environment of the service, or, when that environment does not set it, with the `cdn.origin` setting of the service ([local settings](settings.md)), which applies to the next description without a restart. When it is not set the description says so in `cdn.reason`; an address is never invented. An installed workspace needs none: the environment serves every module of its graph, and `cdn.reason` says that too. A value that is not an http or https origin fails the start of the service. The paths and queries are written by the codec of the compiled-module contract, which makes them the same resource on both origins.

**Externals on the CDN.** With `externals: cdn` and a CDN origin, an installed package this environment would serve (the row "installed for the package that imports it" above) is addressed on the CDN instead, at its installed exact version, under the registry its installation came from (the `resolved` address its lockfile recorded) and with the published options. Every importer resolves it through the one import map of the page, so one copy of a framework is loaded: React and its renderer, and what they import, come from the CDN for every module of the page, the ones in development included. What such a package imports is still known, because this environment compiles it to read its imports (analysis is not delivery), and those imports follow the same rule. The packages the toolchain supplies and publishes in no registry (the development runtime, Widgets and the framework adapters) stay on this environment whatever the selection says, and their records say so in `reason`. Every address on the CDN in the description is checked with a `HEAD` request before the document gives it, without following redirects, at most eight at once, each bounded by `BEYOND_PREVIEW_CDN_TIMEOUT` (5000 ms by default, or the `previews.timeout` setting when the environment does not set it); an output the CDN answered for is not asked again for ten seconds. An address is bound only to an answer that is the output itself: a 2xx, the media type of its family (`application/javascript` or `text/javascript` for a module, `text/css` for a stylesheet) and the strong `ETag` the compiled-module contract defines as the SHA-256 digest of the body. The import map then pins that digest as the address's `integrity` (`sha256-<base64>`, `importmap.integrity`), and the document's link of a stylesheet on the CDN carries it, so a browser loads the bytes the CDN answered for or nothing. Anything else gives no address, leaves the import map and is replaced by nothing, neither this environment's build nor another version: an output the CDN answers it does not hold is `unresolved` with `PREVIEW_CDN_MISSING`; an answer the address cannot be bound to (a redirect, another media type, no digest) is `unresolved` with `PREVIEW_CDN_UNVERIFIED`; a CDN that does not answer within the bound, cannot be reached or answers 5xx is an outage, not a refusal, and the module is `unresolved` with `PREVIEW_CDN_UNAVAILABLE` until a later description finds the CDN answering. Where a scope gave an importer a version that has no address while the page imports another one, the scope maps the specifier to a module that throws the reason (`data:text/javascript,`), so the importer never falls back to a version it does not depend on. Without a CDN origin the externals have no address and are `unresolved` with `PREVIEW_CDN_UNSET`, as a package that is not in development is. Under `environment` nothing is asked of the CDN. An installed workspace (`beyond install`) is not routed by the externals: every node of its graph is served here, and `selection.reason` says so.

What binds the source is the address: the CDN indexes its shared outputs by the registry identity of the package (`/m/<name>@<version>/…` for npm, `/m/<registry id>/<name>@<version>/…` for another registry), so an answer at that address is the CDN's output for that registry's release of that name and version. The integrity of the release's archive is not compared with the one the lockfile recorded, because no answer of CDN delivery identifies the archive an output was prepared from: neither the compiled-module contract nor CDN exposes it (no response header or document of the shared origin names a package's `dist.integrity`), and the host's facade does not read the lockfile's `integrity` either. Until both exist, an output of a registry that serves different archives under one version cannot be told apart; the pinned digest still guarantees that the page runs the bytes the CDN answered for when the description was built. Stylesheets that a widget adopts at run time (it resolves `<specifier>.css` and links it itself) are checked like any address but carry no integrity, since a link the runtime writes does not read the import map's.

Every address of this environment is **relative to the document**, and the document names neither the origin of the service nor any credential. That is what lets a Workspace administration publish a preview behind an authenticating proxy under a path prefix: the proxy adds the `Authorization` grant to the document, module, update and event requests, and the browser never holds it. A visitor grant needs `artifacts.read` and `events.subscribe` only: nothing a preview page loads reads the session description, which describes the whole workspace and its installation. `GET /preview` redirects to `preview/`, relative as well. The document asks for no icon and sends no referrer, because a visitor link may carry its authorization in the path and the CDN is another origin.

**An installed workspace.** When the host serves the workspace from its execution projection ([local installation](local-installation.md#the-development-service-in-install-mode)), the graph of the preview is walked by the edges of its instances instead of what is installed on the disk: every package an importer imports is the instance its own edges select, a peer is the release that an instance which reached the importer provides, nearest first, and an import the graph does not provide is reported (`DEPENDENCY_NOT_INSTALLED`) and has no address: the import map maps it, in its importer's scope, to a module that throws that diagnostic, so the page fails at the import instead of resolving it through another importer's entry. A package of the store that does not build, or whose sources are missing, is `unresolved` with its diagnostic and never served, and a stylesheet selected by specifier follows the same edges, never the disk, the toolchain or the CDN. The runtime the modules import, which a package need not declare, is one instance for the whole page: the one the entry package's own edge selects, else the only instance of that name in the graph; otherwise it is reported as `RUNTIME_NOT_INSTALLED`, never taken from the toolchain, and the coordinator that applies updates is that instance's. An import map holds one address per importer and specifier, so a page whose graph would bind one package instance to two releases of a peer, as two applications that provide two versions of React to one shared widget do, is refused with `409 PEER_CONTEXT_AMBIGUOUS` and its diagnostics rather than given either release: such applications are previewed one at a time.

The entry module is named with `?entry=<public specifier>`. Without it, the entry is the only public module that is built for browsers and that no other public module of the workspace imports; the modules of a runtime package are not applications. Several candidates, or none, answer `409 PREVIEW_ENTRY_REQUIRED` with the candidates and the diagnostics of the ones that do not build, and so does a specifier that several local versions of one package publish, with their versioned specifiers as candidates: `?entry=<versioned specifier>` names one of them. While a module does not build, what it imports is unknown, so the entry that was unambiguous before the error stays the entry. Compiler and dependency diagnostics of the graph are part of the description, and the document logs them to the console of the page.

**Updates.** The Dev Server applies nothing to a page: the runtime does. When the runtime the artifacts are assembled against publishes a `main` module — a workspace package that contains it, or else the runtime package installed with the service, whose manifest exports `./main` — the document imports that coordinator and calls `local.register({ origin, options, session })` with the base of the preview before it imports the application, and `updates.runtime` names it. A coordinator the workspace does not contain is addressed like any module that is not in development: on the CDN, at the version the runtime resolves to. This is a provisional convention, like the `/u/` route.

When the coordinator also publishes `Preview` (the development runtime does), the document starts it with the diagnostics of its description and hands it the failure of the entry's import: the page then shows a development overlay of what does not build (each located error with its file, line, column, frame and message) and of what the page throws, removes it when the correction arrives, and loads the document again when an update cannot be shown in place (a `reload` of the coordinator: an update no module accepted, or a module no longer composed at runtime) or when its entry did not load and a build of every module succeeds. The overlay reads only what the coordinator receives, so a visitor's grant suffices; a reload is never reported as an update. A coordinator without `Preview` only applies updates, and a failed entry import is thrown as before.

`updates.session` is what the runtime needs of the session to apply updates, and the document gives it to the runtime so that it never requests `/session`: the options of the modules in development and, by specifier, each of them as `{package, vspecifier, path}`. Every one of those modules is already addressed in the import map the visitor received, and nothing else is included — no workspace root, installation, process or filesystem location. When the runtime has no coordinator, which is the case of the published Kernel, `updates.reason` says that nothing applies updates to the running page: new code then appears when the document is loaded again, which is a reload and is never reported as an update.

### The composition document

`GET /preview/composition.json?entry=` answers a `composition` document (protocol `beyond-dev-composition/1`) for the same entry, chosen the same way: the packages, the public modules and the public dependencies of the application, in three lists kept apart, for a client that shows the composition and compares one with another. It describes and decides nothing: it is read from the same walk as the preview description, under the same selection and externals.

- **Modules**, by identity: `<package id>/<subpath>`, or the package id for the root subpath. Each has its output for each platform it is described for, with where that output comes from (`source`: `workspace` for a module in development, `environment` for what this environment serves otherwise or what its Node consumer resolves from the installation, `cdn`, or `unresolved` with the reason) and what is known of it (`state`): this environment's build (`built` with its `hash`, or `failed`), or what the CDN answered for its address (`prepared` with the `digest` of its entity tag, which the import map pins; `missing`, `unverified` or `unavailable` for an output left `unresolved`), or `unknown` when nothing was measured. The hash of this environment's build of a package the page takes from the CDN is not reported: it is not the output the page loads. `loaded` says whether the preview page of the entry loads the module. The web outputs are the page's; every public module of the workspace that declares Node is described with its Node output and the Node builtins it imports, since a Node consumer of this environment loads it from here whatever the selection says.
- **Packages**: `<name>@<version>`, prefixed with its registry id and a colon when it comes from a registry other than npm, so two installations of one name stay two packages. `source` is the source its modules' outputs share, or `mixed` when they differ (a selection of single modules, or a package the page takes from the CDN while Node resolves it from the installation); `provider` says who provides its sources (`workspace`, `toolchain`, `installation`, `store`, `registry`); `dependencies` lists what its manifest declares, by kind, with the versions of each name its modules reach in this composition.
- **Edges**: one public import of one module by another, for one platform, between module identities; `runtime` marks the runtime an artifact is assembled against, which its sources do not import.

The files of a module are not part of it: they are the file contract's. It is served with the preview and under the same access (`artifacts.read`): on a pairing service the preview listener answers it to any page, as it answers the preview description, and the API answers it to paired and local callers. So it carries nothing a visitor must not read: no source file, no file, batch or export event, no credential, no address of the API, and no location of this machine (an absolute path, a `file:` address or a Windows path in a diagnostic or a reason is cut to its last segment, as in the preview description). What it does disclose to whoever can open the preview is the shape of the workspace: its public modules, the Node ones included, their output hashes, and the dependency ranges its manifests declare. A service that mounts the route lists `composition` among the capabilities of its session.

## Access

In a Workspace project environment every route, including artifact and event routes, requires a `beyond-dev-grant/1` bearer grant signed by the central administration. The Dev Server holds the authority's public keys, its own environment identifier and the latest signed revocation list. It holds no users, teams or roles.

| Capability | Allows |
| --- | --- |
| `session.read` | Session description |
| `files.read` | Tree and content |
| `files.write` | Mutations and batches, and an installation of the workspace (`POST /installation`, as any method of that path other than `GET` and `HEAD`), which writes the committed lock and `.beyond/` in the working copy and makes registry requests |
| `events.subscribe` | The event stream |
| `inspect.read` | Package, module and dependency inspection, the state and selection descriptions (`/state`, `/selection`), the state of the installation (`GET` and `HEAD /installation`), reading the development selection, the declaration of a module and [type browsing](#type-browsing) |
| `build.control` | Requesting and cancelling builds, and replacing the development selection: it decides what this environment builds and serves for development, it is not a source write, and a viewer does not hold it |
| `process.control` | Starting and stopping development processes |
| `artifacts.read` | Compiled modules and their updates (`/m/`, `/u/`), the resolution documents (`/resolution.json`, `/importmap.json`), the preview entry and the composition document (`/preview/composition.json`), for a preview or a runtime |
| `repository.read`, `repository.write` | Git state, and commit or push |

The guard reads a path as the routes of the service match it, without regard to case or to trailing slashes, so `/Installation` or `/state/` needs the same capability as `/installation` and `/state`. A refusal is `401` with `GRANT_MALFORMED`, `GRANT_KEY`, `GRANT_SIGNATURE`, `GRANT_ISSUER`, `GRANT_AUDIENCE`, `GRANT_EXPIRED` or `GRANT_REVOKED`, or `403` with `GRANT_CAPABILITY`. Expiry and revocation also end open event streams with `access.ended`. A subscriber whose grant lacks `files.read` receives no `file.*`, `batch.*` or `export.*` event: they name source files, who changed them and the packages exported, and a preview visitor subscribes only to learn about builds. The standalone command-line service keeps its loopback binding and owner token; delegated access is the mode of a Workspace environment, not a new requirement of the standalone tool.

**A hosting service that pairs browsers** (the command line starts it so) decides in local mode who each request comes from and leaves its decision on the request under `Symbol.for('beyond.caller')` (`Access.CALLER`); this module keeps no pairing, user or role of its own and reads that decision. A local tool, which presents the service's local credential, and a paired page hold every capability; a local consumer holds `session.read`, `inspect.read`, `artifacts.read` and `events.subscribe`; a request of the preview listener holds `artifacts.read` and `events.subscribe`; anyone else holds none. A capability the caller lacks is refused with the caller's reason (`PAIRING_REQUIRED`, `PAIRING_EXPIRED`, `PAIRING_REVOKED`, `PAIRING_ORIGIN`, `CREDENTIAL_REQUIRED`), a stream of a caller without `files.read` carries no source or export event, and a stream a paired page opened ends with `access.ended` and `PAIRING_EXPIRED` or `PAIRING_REVOKED` when its pairing ends. The hosting service's own rules, the two listeners included, are in [portable connections](portable.md). The host's own events (`export.changed`) reach this module through the `events` of its context and are appended to the log, ordered with its own.

## HTTP mapping

The mapping uses standard preconditions so that the existing entity-tag helper and HTTP caches behave correctly. Paths are percent-encoded per segment.

| Operation | Request | Success | Refusals |
| --- | --- | --- | --- |
| Tree | `GET /files/tree?path=&depth=&scan=` | `200` tree | `404 FILE_NOT_FOUND` |
| Read | `GET /files/content/<path>` | `200` bytes, `ETag: "<revision>"`, `Beyond-Cursor`; `304` with `If-None-Match` | `404 FILE_NOT_FOUND` |
| Create or edit | `PUT /files/content/<path>` with `If-None-Match: *` or `If-Match: "<revision>"` | `200` result | `409 FILE_CONFLICT` with the result, `428 PRECONDITION_REQUIRED`, `413 FILE_TOO_LARGE` |
| Delete | `DELETE /files/content/<path>` with `If-Match` | `200` result | `409`, `428` |
| Rename, batch | `POST /files/operations` with `{mutations: […]}` | `200` batch | `400 PATH_INVALID`, `403 PATH_FORBIDDEN` |
| Events | `GET /events?cursor=` or `Last-Event-ID`, `text/event-stream`, `id:` is the cursor | stream | `400 CURSOR_INVALID` |
| Builds | `POST /builds`, `GET /builds/<id>`, `POST /builds/<id>/cancel` | build | `404` |
| Selection | `GET /development/selection`; `PUT` with `{packages?, modules?, externals?}`; `DELETE` forgets it | `200` selection | `400 SELECTION_INVALID` |
| Declaration | `GET /declarations/<specifier>` (`@scope/name@1.0.0/subpath`, or the bare specifier of a workspace module) | `200` `text/plain` declaration, `ETag: "<hash>"`, `Beyond-Cursor`; `304` with `If-None-Match` | `404 DECLARATION_NOT_FOUND`, `422 DECLARATION_INVALID` with the located diagnostics |
| Types | `GET /types?specifier=&importer=` ([type browsing](#type-browsing)) | `200` `beyond-types/1` document; `Beyond-Cursor` for a generated declaration | `400 TYPES_REQUEST_INVALID`, `403 TYPES_ACCESS`, `404 DECLARATION_NOT_FOUND`, `404 DECLARATION_PRODUCER_MISSING`, `422 DECLARATION_INVALID`, `422 TYPES_UNSUPPORTED` |
| Preview | `GET /preview/?entry=`, `GET /preview/entry.json?entry=`, `GET /preview/composition.json?entry=`; `GET /preview` redirects with `308` | `200` HTML, `200` preview, `200` composition | `404 PREVIEW_ENTRY_NOT_FOUND`, `409 PREVIEW_ENTRY_REQUIRED`, `409 PEER_CONTEXT_AMBIGUOUS` |
| Revocations | `PUT /access/revocations` with the signed list as body | `204` | `401`, `409 REVOCATIONS_STALE` |

`PATH_FORBIDDEN` covers a path that resolves outside the root through a symbolic link and a path through a `.git` or `.beyond` directory at any depth, compared without regard to case: the internals of a repository, a nested one's included, and the state of the service. A request body is parsed only when it is sent as `Content-Type: application/json` (`415 CONTENT_TYPE_UNSUPPORTED` for a batch sent as anything else, and for `POST /builds` or `POST /builds/<id>/cancel` sent with a form or text type), because a page of another site can send a text body to any origin without asking first. The revocation route needs no bearer: the list is self-authenticating and ordered.

The declaration route serves the public declaration of a workspace module as the `ts` bundler emits it: one ambient module declaration whose public type imports keep their bare specifiers and whose internal files stay hidden. It needs `inspect.read`. The tag is the hash of the declaration, the one the build names; the cursor is the one of the source log the answer is consistent with. A bare specifier is resolved to the one version the workspace holds. For a name the workspace holds in several versions, request the versioned specifier: the route does not refuse a bare one with `PACKAGE_AMBIGUOUS`, and answers the first version the service lists. The declarations of installed packages are not served by this route: an editor that checks a source against `react` resolves that package's own declarations, and [type browsing](#type-browsing) reads them for a client that shows them. `types=true` on a compiled-module request stays `OPTION_UNSUPPORTED`, because the compiled-module contract defines no declaration family; this route is the development contract's, for the editor of a workspace, not a delivery of published declarations.

## Type browsing

`GET /types?specifier=&importer=` (`beyond-types/1`, the `types` capability of the session) answers the declaration a consumer's type check reads for a public module, with its provenance, or the precise reason there is none. It needs `inspect.read`, as the declaration route does, whose contract it leaves as it is. It is implemented by [Types](../modules/development/types/index.ts), mounted with the other routes of this module.

- `specifier` is a bare public specifier (`react`, `@scope/name/sub`) or, for a module of the workspace, a versioned one (`@scope/name@1.0.0/sub`).
- `importer` says where the type check resolves it from: a public module or package of the workspace, bare or versioned, or `.` for the root of the workspace, which is the default; each further `> <package>` names a package the previous one imports (`@scope/app@1.0.0/main > react-dom`), so a declaration read in an installed package is followed from that package, as the type check follows it. Each answer gives its `references` with the importer to send back.

```json
{
	"protocol": "beyond-types/1",
	"specifier": "conditioned",
	"importer": "@scope/app@1.0.0/main",
	"provenance": "package",
	"package": { "name": "conditioned", "version": "2.0.0", "provider": "installation" },
	"file": "dist/index.d.ts",
	"form": "declaration",
	"text": "import type { Options } from 'typed-lib';\n…",
	"etag": "sha256-…",
	"references": [{ "specifier": "typed-lib", "importer": "@scope/app@1.0.0 > conditioned" }]
}
```

| Provenance | What is answered |
| --- | --- |
| `generated` | A public module of the workspace, or one the toolchain supplies: the consolidated declaration its bundler's `types` conditional generates, the text `GET /declarations` serves, with `vspecifier` instead of `file`, the declaration's hash as `etag` and the cursor of the source log in `Beyond-Cursor` |
| `package` | An installed package's own declaration, found as TypeScript's `bundler` resolution finds it: the subpath's `exports` target under the `types`, `import` and `default` conditions, in the package's order, a JavaScript target replaced by its declaration (`.js` by `.ts`, `.tsx` or `.d.ts`, `.mjs` by `.mts` or `.d.mts`, `.cjs` by `.cts` or `.d.cts`); without `exports`, `typings`, `types` or `main`, then `index`, and for a subpath its file or directory. A package that publishes TypeScript sources answers the source the type check reads, with `form: source` |
| `types-package` | The `@types` package that types it (`@types/scope__name` for `@scope/name`), reachable as the package is |

The package is the one the importer reaches. With an installed graph ([local installation](local-installation.md)) it is the node the importer's edge binds, peers decided by the chain, and its `@types` package is the one the importer declares; nothing falls back to anything else, and `provider` is `store`. Without one it is the nearest `node_modules/<name>` from the importer's directory upwards, with `node_modules/@types/<name>` beside each, as a type check looks for them (`provider: installation`); when nothing of the name is installed for the importer, the installation that runs Packages is searched the same way, as the type check of such a workspace falls back to it (`provider: toolchain`). `typesVersions`, versioned `types@` conditions and custom conditions are not read.

| Refusal | Status | When |
| --- | --- | --- |
| `TYPES_REQUEST_INVALID` | 400 | No specifier, a path instead of one, a malformed importer chain, or `.` in an installed workspace whose root is not a member |
| `DECLARATION_PRODUCER_MISSING` | 404 | The module's bundler has no `types` conditional, which the esbuild packaging mode does not have (the development runtime's `bundle` today): the error names the bundler (`bundler: {name, specifier}`). No producer of declarations is implemented for it, which says nothing about whether its sources are typed |
| `DECLARATION_NOT_FOUND` | 404 | A module the workspace does not publish, a versioned specifier of a package the workspace does not contain, an importer that is not there, or a package that declares nothing for the subpath (excluded, not exported, JavaScript only) with no reachable `@types` package; `reasons` says what each package tried lacks |
| `DECLARATION_INVALID` | 422 | A generated declaration of a module that does not check, with the located diagnostics; a file that is not UTF-8 text |
| `TYPES_UNSUPPORTED` | 422 | A style module (its `exports` target is a stylesheet), a Node builtin (`fs`, `node:fs`, declared ambiently by `@types/node`), a Git or archive address, a package installed from Git or an archive address (it has no registry identity), and a file larger than 1 MiB (`size`, `limit`) |
| `TYPES_ACCESS` | 403 | The package names a file outside itself (`"types": "../…"`, an `exports` target with `..`), or the real path of the file, symbolic links followed, is outside the package |

Only files inside the resolved package are read, within the bound, and nothing is synthesized: no stub, no inferred declaration, no `@types` package that is not installed. The route reads; it never installs, fetches or builds anything but the generated declaration a workspace module's `types` conditional already builds on request. [The type browsing validation](../tests/types/README.md) runs every case against the real service started from this checkout; resolution through an installed graph is implemented and not run by it.

## Implementation and limits

`Development` composes the collaborators: `Files` (root rules, revision index, mutations, disk observer), `Log` (epochs, cursors, replay), `Builds` (input correlation over the host's delivery facade), `Selection` (the persisted development selection), `Preview` (the graph of the entry module with its addresses, and the entry document) and `Access` (grant verification, stream expiry and revocation). The preview compiles and classifies nothing: it asks the host facade for each artifact's public dependencies and runtime, and maps them to addresses. The one thing it reads by itself is the installed version of a package that the workspace does not contain; in an installed workspace it reads nothing from the disk, and the execution projection the host serves decides. The module exports `guard(app, context)` and `setup(app, context)`, the two entry points the hosting service calls for an extension: `guard` is mounted before the service's own routes so that the session, state, selection, installation, attachment, resolution-document, compiled-module and update routes require a grant too, with a capability per method where one path reads and writes (`GET` and `HEAD /installation` need `inspect.read`, any other method `files.write`); `setup` mounts the routes of this contract. `context` is `{ delivery, settings }` with `settings.root` and, for the preview, `settings.runtime.base`, the installation the runtime resolves from.

Access is configured by the environment, never by a request: `BEYOND_AUTHORITY` (issuer and public keys, JSON) and `BEYOND_ENVIRONMENT` select delegated mode; without them the mode is local and nothing is required, which is the standalone command-line service. `BEYOND_TRUST_LOOPBACK=1` lets loopback requests through without a grant; a Workspace project container sets it because loopback there means processes that already hold the working copy, and routed requests never arrive on loopback. It must stay off wherever a proxy in the same network namespace forwards external requests.

Every read of disk that updates the index runs in one sequence with mutations, so a watcher hint never observes the middle of an API write. The disk observer only supplies hints; each hint is compared with disk, and a scan compares everything. On macOS and Windows it is Node's recursive `fs.watch`, which is the operating system's own; elsewhere it is one non-recursive watch per visible directory ([Directories](../modules/development/directories.ts)), because Node emulates a recursive watch on Linux by watching each file by its inode: a file replaced by a rename (a temporary file renamed over it, as editors, formatters, Git, AI engines' tools and the File API itself write) was announced once and never again, so its later edits reached neither the events nor a build until a scan. `BEYOND_DEVELOPMENT_WATCH=directories` selects the watch per directory on any platform, which is how a macOS run validates it ([tests/development/replaced.test.mjs](../tests/development/replaced.test.mjs)). Compilation keeps its own invalidation through the watchers service. Before each build the host is asked to refresh its declarations, because manifests are not watched by the compiler.

Validation, from the repository root with the bootstrap Engine serving this implementation:

```sh
BEE_URL=http://localhost:1112 node --import "$BEE_NODE_DIR/register.mjs" tests/development/index.mjs [files|service|diagnostics|access|preview]
BEE_URL=http://localhost:1112 node --import "$BEE_NODE_DIR/register.mjs" --test tests/development/contract.test.mjs tests/development/preview.test.mjs tests/development/preview-externals.test.mjs tests/development/preview-composition.test.mjs
```

The schema and its fixtures are checked without an Engine, with `node --test contracts/development/test/fixtures.test.mjs`. That test imports `ajv`, which this repository does not declare: it resolves today because an installed dependency brings it, so declare it before relying on the check in automation.

The `files` group runs the source and event scenarios against real disk writes and the real watcher. The `service` group runs the shared grant vectors, the HTTP preconditions, stream revocation and expiry, and build correlation; its build cases use a stand-in delivery so that timing can be driven, and say so in their name. The `diagnostics` group runs the build's diagnostics over a stand-in delivery whose answers are those the real compilers give: a syntax error that two modules meet and both the transformation and the type check report, listed once with its frame and `modules`; a supplied package's type error left out; and the `files` of a build. The `preview` group runs the selection and preview scenarios over the same stand-in delivery: persistence, access, the addresses with and without a CDN origin, and the event filter. `preview.test.mjs` runs the preview over the real delivery of [a fixture](../tests/development/fixtures/contract/README.md) with installations from npm, from another registry and from Git: the source of each address, the scope of an importer of another version and the CDN address of an unselected package published to another registry. `preview-externals.test.mjs` runs the externals of the selection over the same fixture with a stand-in CDN origin that answers `HEAD` with an entity tag: the default that changes nothing, both installed versions of `library` addressed on the CDN in their scopes, a missing output left unresolved and out of the import map, a scoped version that fails in its scope instead of falling back, a CDN that does not answer within a 400 ms bound, no origin, a supplied package kept here (a stand-in facade marks it), and the validation, storage and announcement of `externals`. `preview-composition.test.mjs` checks the composition document of the fixture against the `composition` definition: packages, modules and edges apart, both platforms' outputs with their hashes, and under `cdn` the digest the CDN answered and a `mixed` package. `contract.test.mjs` runs the compiled-module routes the service mounts over the same fixture ([the tests' guide](../tests/development/README.md)). The `access` group runs the guard over stand-ins of the routes the hosting service mounts itself: in delegated mode the installation routes (`inspect.read` to read, `files.write` to install) and the resolution documents (`artifacts.read`) are refused without a grant (`401`) and with another capability (`403`), and in local mode none needs one. The preview and the resolution documents of an installed workspace are executed by the local installation's `serving.test.mjs` ([its guide](../tests/local-install/README.md)). Real compilation behind this contract is validated through the Workspace project environment, which runs the hosting service in Docker, and [the preview validation](../tests/preview/README.md) runs the real service in delegated mode with a real browser: the routing of a module that is not selected, rendering behind a path prefix, and an update applied to the running page.

Limits of the current implementation:

- Build diagnostics are located only when the processor that produced them named the source file: the `ts`, `styles`, `vue`, `svelte` and `tsc` processors do; a diagnostic of a manifest, a dependency or the delivery itself carries the message only. The frame is read when the build reports the diagnostic, so an edit saved in between makes the build `superseded` rather than its frame wrong.
- A build is `superseded` when any source file changed after its input cursor, not only one of its own inputs. That is conservative: it can discard a result that was still valid, never publish one that was not.
- `inspect.read` routes for packages, modules and dependencies, `process.control`, the repository capabilities and the legacy inspector adapter are not implemented.
- Grants travel only in the `Authorization` header, and a browser cannot add one to a module request. The preview is therefore designed for an authenticating proxy that adds it, which the preview validation exercises with a stand-in gateway; the proxy of a Workspace administration, its visitor links and their revocation are not part of Packages and were not validated here. Without such a proxy a browser reaches a preview only in local mode or over a trusted loopback.
- Nothing is hosted at a CDN origin today. A preview of a workspace that was never installed needs from that origin every package that neither the workspace, the toolchain's supplied packages nor the installation of its importer provides, so until one exists `BEYOND_CDN_ORIGIN` must name a service that implements the compiled-module contract and answers cross-origin module requests (`Access-Control-Allow-Origin`). The dependencies of a module delivered by the CDN are read from its source in the workspace when it has one; the dependencies of a package the workspace does not contain and does not install are unknown to this service. The contract now defines the route of a release's resolution (`/_r/<n>/resolution.json` on a CDN application host), but the preview does not read it: a preview is not bound to a release.
- A preview applies updates only when the runtime of its artifacts has a coordinator, in the workspace or installed with the service. The development runtime is installed beside Packages under its provisional name (`@beyond-js/local-2026`) by the command line's acceptance installer and by the Workspace environment image; it is published in no registry and delivered by no hosted CDN. The service compiles and serves it, with the Widgets package and the framework adapters, as packages the toolchain supplies, so a preview needs no stand-in for them; a project that uses the published Kernel is rebuilt on save and shown on reload. A workspace installed with `beyond install` receives none of them from the toolchain: its runtime is the page's runtime instance in the installed graph (`RUNTIME_NOT_INSTALLED` when the graph has none), and the coordinator that applies updates is that instance's ([local installation](local-installation.md#the-development-service-in-install-mode)).
- The stylesheet of a module is applied by the runtime to whoever holds it (see [Builds](#builds)); the code of a module compiled in the esbuild packaging mode is still shown on reload only.
- The selection has no revision: a replacement is last-write-wins, which fits one environment per user and project.
- Directory deletion and empty directories are not operations of the contract.

## Legacy inspector compatibility

The legacy inspector protocol is preserved for its existing consumers until an explicit migration. It is an adapter over the same operations, not a second file service.

| Legacy identifier | Disposition |
| --- | --- |
| `rpc-v2` / `response-v2-<id>` envelope | Preserve for legacy clients; new clients use this contract |
| `sources/save`, `sources/create`, `sources/rename`, `sources/delete` | Adapter onto mutations. The legacy payload has no revision, so the adapter reads the current revision and states it; a concurrent change surfaces as a legacy error instead of a silent overwrite |
| `sources/format` | Preserve as a stateless operation |
| `processors/sources/list` and `data` with the `{tu, data}` envelope | Adapter onto tree and read. The row shape `{id, version, code, hash, file, …}` is kept; `hash` maps to the revision |
| `bundle/change`, `application-styles`, `global-styles` | Preserve verbatim: shipped `@beyond-js/local` runtimes consume them |
| `project-process:<id>` | Preserve as a projection of build events |
| `dashboard/validate` | Not an authorization mechanism; delegated grants replace it in Workspace environments |

Legacy operations that never worked (`sources/clone`, `builder/module/delete`, rename through the missing `fs.rm`) carry no compatibility obligation beyond their names.
